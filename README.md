# Fiddler Classic

## Introduction

Fiddler Classic is a Windows desktop HTTP debugging proxy used to capture, inspect, and troubleshoot traffic exchanged between client applications and remote services. It operates as an intermediary proxy on the local machine, allowing engineers to observe individual HTTP and HTTPS transactions rather than relying only on application logs. Each captured session can expose the request method, target URL, headers, cookies, status code, payload, content type, redirects, and timing data required to diagnose protocol-level failures.

The tool is useful when investigating REST API errors, authentication problems, incorrect request formatting, unexpected server responses, caching behavior, redirect loops, and differences between browser and desktop application traffic. HTTPS inspection requires traffic decryption to be enabled and the local interception certificate to be trusted by the client environment. Applications that use certificate pinning or a custom trust store may reject intercepted TLS connections.

Fiddler Classic also provides a controlled way to reproduce network activity. Engineers can isolate a small set of sessions, compare successful and failed requests, replay transactions, modify request data, or substitute responses during testing. In operational environments, an essential prerequisite is confirming that capture mode is active before reproducing a problem; otherwise the target application may run while Fiddler records nothing.

Captured sessions should be treated as sensitive diagnostic data. Authentication headers, session cookies, API tokens, form values, and personal information may be visible in clear form after decryption, so capture files should be sanitized before they are shared or archived.

## Installation and Capture Readiness

Install Fiddler Classic on the Windows workstation from which the target traffic will be generated. In managed or vendor-controlled environments, use the exact build that has been validated for the connected application or device. A different build may introduce compatibility differences, so replacing a prescribed version should be treated as a configuration change and tested before production troubleshooting.

When installation media is provided as an archive, extract it locally and start the installer with administrative privileges. Administrative elevation is important because setup may need to write application files and system-level configuration. Accept the license terms, select the required installation directory, complete setup, and close any post-installation window that is not needed for the troubleshooting workflow.

On some deployments, the Start menu entry is displayed as `Fiddler 4`. During the first launch, an initialization dialog may appear; if the deployment procedure does not require additional configuration at that point, dismiss it so the main capture window opens.

Before starting the target application, verify the lower-left status area. The word `Capturing` indicates that session capture is enabled. If that area is blank, Fiddler is not actively capturing; click the status control to enable capture before reproducing the issue. This check is operationally critical because a disabled capture state can be mistaken for an application or connectivity problem.

A reliable workflow is: start Fiddler, confirm `Capturing`, minimize the window, execute one controlled operation in the target application, return to Fiddler, and inspect only the sessions generated by that action.

## Capturing and Inspecting Traffic

Keep the capture scope as small as possible. Clear unrelated sessions before reproducing a fault, then perform a single transaction such as login, data transfer, API submission, or synchronization. This produces a compact session sequence that is easier to correlate with the user action and reduces the risk of overlooking the request that actually failed.

For each relevant session, inspect the request and response separately. Start with the HTTP method, host, path, query string, response status, and redirect behavior. Then examine headers such as `Authorization`, `Cookie`, `Content-Type`, `Accept`, cache directives, and custom application headers. For payload-bearing requests, validate that the body format matches the declared content type. A request labeled as JSON but containing malformed JSON, for example, can produce a server-side `400` response even though TCP and TLS connectivity are working normally.

When HTTPS decryption is enabled, Fiddler can expose application-layer data. If the client refuses the connection after interception is enabled, investigate certificate trust, application-specific trust stores, or certificate pinning before treating the failure as a server outage.

Use timing data to distinguish transport delay from application processing delay. A long interval before the first response byte suggests a different problem from a large response that downloads slowly. Compare a failed transaction with a successful one and focus on fields that differ.

In some integrated applications, temporary HTML markup can appear in the interface while a request is being processed and disappear when processing finishes. Treat this as an intermediate rendering state unless it persists afterward.

## Replaying and Modifying Requests

Captured traffic can be reproduced under controlled conditions. Composer allows engineers to take an existing request, resend it, and modify selected fields without repeating the complete application workflow. This is effective for isolating whether a failure is caused by authentication, headers, payload structure, query parameters, or server-side processing.

For example, if a POST request returns `400 Bad Request`, replay the same transaction while changing only one variable at a time. Correct the `Content-Type` header, remove a questionable JSON property, replace an expired bearer token, or adjust a query parameter. If the response changes after one modification, the test provides a stronger diagnostic signal than repeatedly exercising the full user interface.

Request and response breakpoints are useful when network traffic needs to be modified during an active client session. A request breakpoint stops outbound traffic before it is sent to the server, making it possible to adjust headers or change the request body. A response breakpoint interrupts inbound traffic before it reaches the client, allowing testers to evaluate application behavior with different status codes, altered headers, or modified response data.

AutoResponder can support frontend and integration testing by returning controlled content for matching requests. Keep such rules narrowly scoped so they do not affect unrelated hosts or sessions.

Use replay features carefully against production systems. `POST`, `PUT`, `PATCH`, and `DELETE` requests can create, modify, or remove data, and replaying an authenticated transaction can repeat the original side effect. Prefer non-production endpoints or transactions known to be idempotent whenever possible.
